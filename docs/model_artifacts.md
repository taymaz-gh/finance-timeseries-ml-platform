# Local model bundles and inference readiness

A successful training run is not automatically an inference-ready artifact. Local inference requires **both the best Keras model and the exact preprocessing fitted during that same run**. The training pipeline therefore creates a separate run directory under the configured `artifact_dir` and publishes a bundle manifest only after training and checkpoint creation succeed.

## Artifact contract

```text
artifacts/synthetic_training/
└── run_<UTC timestamp>_<unique ID>/
    ├── best_model.keras
    ├── preprocessing_metadata.json
    ├── bundle_manifest.json
    ├── training_history.csv
    └── learning_curve_*.png
```

`best_model.keras` is selected by **validation macro-F1**, using the existing Keras `ModelCheckpoint` callback. The accompanying `preprocessing_metadata.json` records the ordered model features, training-fitted imputation medians, categorical levels, scaling parameters, chronological training/validation boundaries, sequence length, stride, number of classes, and boundary-trimming width. `training_input` distinguishes a supplied in-memory Gold DataFrame from a Databricks table query. A configured `source_table` is not proof that the table was queried when Gold was supplied directly.

The versioned `bundle_manifest.json` records the expected artifact filenames, file sizes, SHA-256 checksums, input/output shape requirements, and model-selection metric. It is written **last and atomically**. An interrupted or failed run may leave other files behind, but without a valid manifest it cannot be loaded as a complete bundle. Separate run directories prevent a new model from being paired accidentally with older preprocessing metadata.

## Training and loading

In `configs/training_synthetic.yaml`, enable `save_keras_checkpoint: true` while keeping `log_to_mlflow: false` and `register_in_uc: false`. Run a small, explicitly requested local experiment:

```powershell
finance-ml train --data-source synthetic --config configs/training_synthetic.yaml --synthetic-accounts 8 --synthetic-days 60
```

The CLI prints the **exact** bundle directory on success. Passing that directory to `load_local_bundle(path)` verifies the manifest, hashes, preprocessing schema and feature order **before** loading the Keras model. The loader then uses `compile=False` and `safe_mode=True` and checks that the loaded model's sequence length, number of features, and number of output classes match the saved metadata. `inspect_local_bundle(path)` performs the file and metadata checks without importing TensorFlow. Neither operation queries Databricks, starts MLflow tracking, or registers a model in Unity Catalog.

The SHA-256 checks guard against accidental mismatches or changes; they do **not** authenticate a maliciously replaced manifest and model. Load serialized models only from trusted sources. Keras bundles and remotely logged MLflow/Unity Catalog models are distinct artifact paths, even when generated by the same training run.

## Requirements for the inference CLI

The inference CLI will accept an explicit bundle directory, apply the **saved** feature ordering and fitted transformations, and reject incompatible input schemas or incomplete artifacts. It must not refit encoders, scalers, or imputers on holdout data.

**Automatic historical-context generation:** Whenever synthetic holdout data are requested for inference on existing accounts, the system must automatically determine and generate the historical observations required for valid predictions, even if the user does not explicitly request them. Context must preserve each account's chronological state and causal feature history. Ground-truth labels remain separate, and only requested holdout timestamps are reported as predictions.

A seven-step model with boundary trimming and overlapping-window aggregation may require more context than six preceding observations. Batch inference can use subsequent *observed, unlabeled* holdout values; live inference cannot use future observations that have not arrived. The inference pipeline must calculate coverage for each requested timestamp and report unsupported boundary predictions explicitly, not silently omit them.

## Spark resource ownership

An explicit lifecycle ownership is implemented so that:

- Caller-provided Spark sessions are never stopped by the runner.
- Sessions already managed by another component are reused safely.
- Sessions newly created for standalone local training are stopped after success or failure.
- Cleanup cannot accidentally hide the original training exception.

The training runner implements this behavior independently of model fitting; its existing-context detection is isolated because it relies on a version-sensitive PySpark internal reference. Long-lived applications should inject externally managed Spark sessions explicitly.
